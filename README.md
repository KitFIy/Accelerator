# Axisec

Шлюз, который стоит между ИИ-агентом и инфраструктурой компании и решает,
какое действие агента можно исполнить. Решение принимает не нейросеть, а
обычный алгоритм: SQL разбирается по синтаксическому дереву, аргументы
вызовов сверяются со схемой, ответы проверяются на секреты и персональные
данные. Запрещённое действие не исполнится, как бы ни был сформулирован
промпт, который к нему привёл.

Проект Акселератора РТУ МИРЭА, технологический трек. Версия MVP 0.1.0.

## Запуск

```bash
pip install -r requirements.txt
python -m axisec            # http://127.0.0.1:8080
```

или в контейнере:

```bash
docker compose up --build   # http://127.0.0.1:8080
```

Интернет и ключи не нужны: в составе есть стенд — демо-магазин с базой CRM,
почтой и платежами, MCP-сервер к нему и имитатор модели.

## Что показать за две минуты

1. Вкладка **Стенд**, сценарий A04 «Отравленный документ». Нажать «Запустить
   сценарий». Слева агент без защиты читает письмо поставщика, находит в нём
   спрятанную команду и переводит 950 000 руб. на чужой счёт. Справа тот же
   агент через Axisec: перевод заблокирован за десятки микросекунд, указано правило.
2. Сценарий A01 «Сброс базы»: слева таблица клиентов уничтожена, справа цела.
3. Вкладка **Проверка вызова**: предложить жюри самим обойти защиту
   (`DrOp/**/TaBlE`, UNION к закрытой таблице, вторая команда через `;`).
   Пример «Опасные слова в данных» показывает обратное: запрос, где
   `drop table` — просто текст в строке, проходит. Фильтр по словам здесь ошибся бы.
4. Вкладка **Red Team** → «Запустить полный прогон»: сводка по всем сценариям.

## Как это устроено

```
                    ┌──────────────────────── Axisec ────────────────────────┐
 агент ──(1)──────► │ /v1/chat/completions   проверка tool_calls в ответе     │ ──► модель
 (base_url шлюза)   │                        модели до их исполнения          │    (GigaChat, YandexGPT,
                    │                                                         │     любая OpenAI-совместимая)
 агент ──(2)──────► │ /mcp/<сервер>          проверка tools/call,             │ ──► MCP-серверы, БД, API
 (URL MCP-сервера)  │                        фильтр tools/list, DLP ответов   │
                    │                                                         │
                    │ движок политик: AST SQL · схемы аргументов · DLP        │
                    │ журнал аудита (SQLite) · дашборд · Red Team             │
                    └─────────────────────────────────────────────────────────┘
```

Две точки контроля:

1. **Ответ модели.** Агент обращается к модели через шлюз (в SDK меняется
   только `base_url`). Шлюз видит вызовы инструментов в ответе модели раньше,
   чем их исполнит код агента, и убирает запрещённые. Работает и для
   инструментов, которые агент исполняет внутри своего процесса.
2. **MCP.** Агент подключается к MCP-серверу через шлюз. Запрещённый
   `tools/call` не доходит до сервера, запрещённые инструменты не видны в
   `tools/list`, секреты в ответах инструментов скрываются.

Подключение своего окружения — через переменные:

| Переменная | Значение |
|---|---|
| `AXISEC_POLICY` | путь к файлу политики |
| `AXISEC_LLM_UPSTREAM` | адрес OpenAI-совместимого API, например `https://llm.example/v1` |
| `AXISEC_LLM_API_KEY` | ключ к модели (иначе пробрасывается заголовок клиента) |
| `AXISEC_MCP_UPSTREAMS` | JSON вида `{"crm": "http://crm-mcp:9000/mcp"}` |
| `AXISEC_AUDIT_DB` | файл SQLite для журнала аудита |

## Политика

Политика — файл YAML (`policies/crm_agent.yaml`). Запрещено всё, что не
разрешено явно.

```yaml
tools:
  run_sql:
    args:
      query:
        type: sql
        sql:
          allow_statements: [select, insert, update]   # DROP, DELETE, ALTER не разрешены
          tables_allow: [customers, orders, tickets]
          columns_deny: {customers: [passport, card_number]}
          require_where: [update, delete]
          max_rows: 50
  transfer_money:
    args:
      amount: {type: number, min: 1, max: 50000}
      to_account: {type: string, enum: ['40702810900000000001']}
  delete_customer:
    action: deny
```

Что умеет проверка SQL: тип операции (в том числе вложенной в CTE и
подзапросы), несколько команд в одном запросе, списки таблиц и столбцов,
системные каталоги, опасные функции, UPDATE и DELETE без WHERE или с
условием, которое всегда истинно, перезапись через `INSERT OR REPLACE`,
размер выборки (LIMIT добавляется автоматически). Неразобранный запрос
отклоняется.

## Ограничения MVP

- Модель на стенде — имитатор, который выполняет любую найденную инструкцию.
  Это худший случай для защиты, но не замена проверке на реальных моделях.
- Детерминизм гарантирует исполнение политики, а не её полноту. Действие,
  разрешённое политикой, пройдёт (например, UPDATE с осмысленным, но слишком
  широким условием).
- Потоковые ответы модели отдаются одним фрагментом после проверки.
- В MCP поддержан обмен запрос-ответ; серверные потоки (GET, уведомления) не
  проксируются.
- Диалекты SQL проверены на SQLite и частично PostgreSQL.
- Нет ролей пользователей, подтверждения человеком и интеграции с SIEM.
